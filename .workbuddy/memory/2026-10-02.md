## picart 通用层（common + config）静态审计

范围：`src/common/`（44 文件）+ `src/config/`（12 文件），不含 `src/modules/` 业务代码。

### 技术栈确认
NestJS 11 + TypeORM(MySQL) + Redis(Keyv/Bull) + Passport-JWT + Swagger。
全局前缀 `api/v1`（main.ts `setGlobalPrefix`）。无 Prisma，无 Nest 内置 AuthModule framework 层。

### 架构事实
- 请求管线：`main.ts` 装 ValidationPipe + TransformInterceptor + LoggingInterceptor + HttpExceptionFilter；
  `app.module.ts` 注册两个全局守卫 `JwtAuthGuard` / `ImageDomainGuard`（APP_GUARD）。
- `PermissionGuard` 不走全局，靠各业务 controller 的 `@UseGuards` 局部挂载。
- 队列 3 条（image-audit / text-audit / video-compression）定义在 `common/queue/queue.module.ts`。

### 发现的问题（按严重度）
1. **`loggerConfig` 完全未接线**：`config/logger.config.ts` 写了完整 winston + 每日轮转配置，
   但 `app.module.ts` 没有 `WinstonModule.forRootAsync(loggerConfig)`，main.ts 也没用 nest-winston。
   → `LoggerUtil` 实际走的是 Nest 内置 Logger，日志落盘/轮转根本没生效。
2. ~~`CommonModule` 未被 import~~ **【已更正，初次判断错误】**：`CommonModule` 实际被
   `user.module.ts`(L25/L57) 与 `payment.module.ts`(L11/L19) 导入，`CommissionService`
   另被 `order.module` 直接列为 provider。均**不是死代码**。
   误判原因：grep `CommonModule` 时 `head_limit` 被 common/ 目录内 LoggerUtil 的匹配刷满而截断。
   教训：查"是否被引用"时不要用会命中同名字符串的高频模式，或直接对整个 src 分文件计数。
3. **`app.config.ts` 未 load**：`ConfigModule.forRoot({ load: [uploadConfig] })` 只加载了 upload，
   `appConfig`（版本/强更/维护模式）定义了却没用。业务侧的 appConfig 实际来自 `modules/config` 的 DB 配置，两者同名易混淆。
4. **`jwtRefreshConfig` 无引用**：refresh token 在 `JwtUtil.generateTokens` 里是用同一个 `jwtService`
   签的，没有用 refresh secret，双密钥设计形同虚设。
5. **契约不一致**：`TransformInterceptor` 成功体 `{code:200,message:"操作成功",data}`（无 timestamp/path），
   `HttpExceptionFilter` 错误体 `{code:status,message,data:null,timestamp,path}`。
   而 `BaseResponseDto` 声明了 timestamp/path → 类型与实际返回对不上。
6. **common 反向依赖 modules（分层倒置）**：`ImageDomainGuard` 依赖 `modules/config/config.service`；
   `PermissionGuard` 依赖 `modules/user` 的 User entity；`CommonModule` 直接 import 6 个业务 entity；
   `sanitize.util` / `permission.util` / `block-status.util` / `user-decorator.util` 全部 import 业务 entity。
7. **业务逻辑混入 common**：`queue/audit.processor.ts`(766 行，图片/文本审核流转)、
   `queue/video-compression.processor.ts`(411 行，视频压缩策略)、`commission.service.ts`(501 行) —— 这些是业务，不是框架。
8. **`ConfigUtil.checkAllConfig` 是空实现**：只 `get` 出变量然后丢弃，永远不报错；
   main.ts 里的 try/catch 属于摆设。
9. `multer.config.ts` 的 `fileFilter` 用请求头 `content-length`（整个请求体大小）判断单文件超限，
   多文件上传时会误判。

### 引用面需复查的工具（下述判断同样受 grep 截断影响，未逐一确认）
`FileTypeUtil`、`PermissionUtil`、`getBlockedUserIdSet`（util 版；业务实际走 `userService.getBlockedUserIdSet`）
疑似零引用。`header.util.getHeaderValue` 已确认被 `user/strategies/jwt.strategy.ts` 使用，引用面窄但非死代码。
